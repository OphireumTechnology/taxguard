## How the copies were made

Six proposals (060000 to 100000) replace existing functions. Each replacement is the **current** definition (the
last definition in execution order, not in filename order) with only the named change applied. The copies were
generated by script from the current text, with an exact-match count required for every edit, and diffed line by
line against the current definition before commit. A reviewer can reproduce the comparison by extracting each
function from the proposal and from the file named on its `-- Current definition:` line.

## Proposals

### 20261018020000: client-ID counter initialization
- **Defect:** no migration created the `primary` counter row. On a fresh database every self-registration was
  refused (`CLIENT_COUNTER_CORRUPT`).
- **Change:** inserts the row once and only moves it forward, to the highest numeric client ID already issued.
  No function changes.
- **Invariants:** no client ID is reissued. The fail-closed refusal for a row that later goes missing is
  unchanged. Re-running is harmless.
- **Evidence:** `clientIdSequence.db` (3), `clientProvisioningConcurrency.db` (3; concurrent provisioning with
  replay, missing counter row).
- **Rollback or recovery:** none needed; the row is the counter the function already expects. **Owner check:**
  confirm whether staging already holds the row.

### 20261018030000: durable Stage 01 onboarding
- **Change:** adds the tables `taxguard_onb_consent_versions` and `taxguard_client_onboarding` and 15 functions.
  It widens the client-notification kinds and adds the `clientOnboardingCompleted` check to case Stage 1.
- **Invariants:**
  - Only the TIN type and its last four digits are stored; a full TIN is refused.
  - Submission needs an APPROVED consent version, and no application role can write one.
  - Approval is a staff decision: manager or administrator, a staff-verified identity document, and a
    duplicate check with a reasoned override.
  - The client view carries no internal notes or decider identities. Every write is versioned and audited.
- **Evidence:** `clientOnboarding.db` (10), `caseOnboardingGate.db` (2), browser journey B (provider suite 14).
- **Blocker:** no consent version is approved. The IRC § 7216 wording needs counsel or practitioner approval, so
  nobody can submit until then (by design).
- **Rollback:** drop the `taxguard_onb_*` functions and both tables, and re-apply the 20261012260000
  definition of `taxguard_case_system_checks`. Identities already marked COMPLETED keep that status.

### 20261018040000: billing transition audit
- **Change:** `taxguard_bill_transition` audits the from and to status, the return or void note, and the issued
  invoice number. Everything else is identical to proposal 028.
- **Invariants:** authorization, maker-checker, numbering and the client projection are unchanged. Audit rows are
  staff-only.
- **Evidence:** `billingTransitionAudit.db` (3).
- **Overlap:** Codex's Phase 15 billing branches redefine `taxguard_bill_*`. Reconcile which definition runs last.
- **Rollback:** re-apply proposal 028's definition.

### 20261018050000: Stage 06 requires an approved workpaper
- **Change:** `taxguard_case_evidence_checks` requires an APPROVED book-to-tax workpaper for the case's client,
  year and return family before the Review attestation.
- **Invariants:**
  - Who attests is unchanged.
  - Draft, rejected, superseded, other-year and other-client workpapers do not count.
  - The check is server-derived.
- **Evidence:** `caseWorkpaperEvidence.db` (3), provider suite 14, Stages 04–08.
- **Rollback:** re-apply the 20261018000000 definition.

### 20261018060000: engagement-scoped documents and Stage 02 (Package A)
- **Change:** adds `taxguard_staff_scope`, the manager exemption plus an ACTIVE effective assignment whose NULL
  engagement or year acts as a wildcard. It changes nine document and collection functions.
- **Invariants:**
  - Managers, administrators and client-wide staff are unchanged.
  - Refusals reuse the not-found and access-denied codes.
  - A refused download writes no audit row.
- **Evidence:** `engagementScopedAccess.db` (6, five failed first), `clientDocumentConfidentiality.db` (7).
- **Rollback:** re-apply the listed proposals' definitions and drop the helper.

### 20261018070000: ledger, book-to-tax and work-queue tax-year scope (Package B)
- **Change:** adds the helpers `taxguard_ledger_year_scope`, `_year_guard` and `_event_year`. It changes 18
  functions and adds two BEFORE INSERT triggers (on `taxguard_ledger_entries.creator_uid` and
  `taxguard_b2t_adjustments.prepared_by`).
- **Invariants:**
  - `taxguard_ledger_actor` is unchanged.
  - A year in the request is refused with `LEDGER_ACCESS_DENIED`; a record addressed by id that is out of scope
    gets its not-found code.
  - Chart of accounts and bank-feed ingestion stay client-level.
- **Evidence:** `ledgerYearScope.db` (9). Five cases failed first; the trigger case was shown to fail with the
  triggers disabled.
- **Amended 2026-10-19:** `taxguard_ledger_trial_balance` accepted any "as of" date, so a member assigned only for
  2024 could request 2024 "as of" a 2025 date and receive 2025 activity in the period. The date must now fall
  inside the requested year (`LEDGER_INPUT_INVALID`). The new case failed first. Codex's `trial_balance_exact`
  delegates here and inherits the fix.
- **Rollback:** re-apply the listed definitions, drop both triggers and the helpers.

### 20261018080000: document-request engagement-year scope (Package B)
- **Change:** reuses `taxguard_staff_scope`. It changes insert (both the requested year and a replayed id),
  list, link, resolve, remind, the missing and review queues, and the client projection.
- **Invariants:**
  - Clients reach only their own client and never see cancelled requests or staff fields.
  - A malware-rejected document is hidden from the client unless a client user uploaded it.
- **Evidence:** `documentRequestScope.db` (7; all failed first).
- **Rollback:** re-apply proposal 20261012310000's definitions.

### 20261018090000: case access follows the live assignment
- **Defect:** a case records its preparer and reviewer at creation, and access was decided on those recorded
  names only. A revoked or expired preparer or reviewer could still:
  - read the case and add notes;
  - advance it, including the reviewer's human attestations;
  - return or hold it;
  - see it in the queue, the status counts and the dashboard;
  - list and record tax-calculation runs (a former preparer);
  - approve a computed tax run (a former reviewer).
- **Change:** adds `taxguard_case_slot_live`. The recorded name now counts only while that person holds an
  ACTIVE, effective assignment of that role for the case's own client, engagement and year. It applies to
  `taxguard_case_actor`, which detail, notes, advance, return and hold use, and to the queue, status report,
  `dash_my_work`, `tax_run_list`, `tax_run_record` and `tax_run_review`.
- **Invariants:**
  - Managers and administrators are unchanged.
  - The recorded names, the two-person rule and every stage check are unchanged.
  - Refusals keep `CASE_NOT_FOUND`, `TAX_CALC_CASE_NOT_FOUND` and `TAX_CALC_REVIEWER_REQUIRED`.
  - `tax_run_review` now uses `IS DISTINCT FROM`, so a missing reviewer is refused rather than compared as NULL.
- **Evidence:** `caseAssignmentRevocation.db` (6). Four failed first. The tax-run approval case was shown to fail
  with only that change removed. It covers:
  - revocation, expiry and restoration;
  - another year or another engagement;
  - reassignment to another person;
  - the case API (`/cases/:id`, notes, queue);
  - earlier notes and the case document;
  - the queue, counts and dashboard;
  - manager and administrator access;
  - cross-client and cross-tenant refusal.
- **Known consequence:** a replacement assignee is not the case's recorded preparer or reviewer, so they cannot
  act on the case until a reviewed case-team operation exists (next package). A manager can act meanwhile.
- **Rollback:** re-apply the 20261012260000, 20261012320000 and 20261012330000 definitions and drop
  `taxguard_case_slot_live`.

### 20261018100000: practice client detail confidentiality
- **Defect:** `taxguard_practice_client_detail` and its write paths decided access per client. An
  engagement-year assignee received:
  - every engagement's internal notes, tasks and deadlines;
  - the whole team and its assignment history;
  - the client's case and ledger activity of every year (bypassing the 070000 ledger history filter).

  They could also add notes, tasks and deadlines to any engagement and year, and resolve its deadlines.
- **Change:** adds four helpers:
  - `taxguard_staff_record_scope`: a record is scoped by the dimensions it carries (engagement and year; engagement
    only; year only; neither means whole-client);
  - `taxguard_practice_item_scope`: a case-linked item takes the case's engagement and year;
  - `taxguard_practice_event_scope`: ledger events by the referenced record's year, case events by their case,
    practice events by their metadata;
  - `taxguard_practice_year`: a safe year parse.

  It changes `practice_client_detail` (every section), `add_note`, `create_task`, `add_deadline` and
  `resolve_deadline`.
- **Invariants:**
  - Managers, administrators and client-wide staff see and change everything.
  - A task assigned to, or created by, the actor stays visible to them.
  - The detail's shape is unchanged; out-of-scope items are omitted.
  - Refusals reuse `ENGAGEMENT_NOT_FOUND`, `CASE_NOT_FOUND` and `DEADLINE_NOT_FOUND`.
- **Evidence:** `practiceClientDetailScope.db` (8; six failed first). It covers:
  - notes, tasks, deadlines, engagements and years, team, history, and ledger and case activity;
  - the write paths, where refused writes leave no rows or audit entries and a replayed out-of-scope task key does
    not confirm the task exists;
  - client-wide staff, managers and administrators;
  - other clients and tenants, and revocation.

  The composition re-apply check caught a missing `REVOKE` on the new year helper before commit.
- **Rollback:** re-apply proposal 20261012250000's definitions and drop the four helpers.

## Codex handoff (Phase 15)

1. **Idempotent replay authorization.**
   - Phase 15's `post_entry(_once)`, `reverse_entry(_once)` and `b2t_prepare_adjustment` return an existing
     record on replay without inserting, so the 070000 insert triggers never see the replay. The current
     definitions have the same gap.
   - On replay, check `taxguard_ledger_year_scope(p_tenant, p_client, p_actor, r, <existing>.tax_year)` and
     refuse an out-of-scope record with the function's not-found code.
   - Billing replays (keyed `addLine`, `requestCredit`, refunds) should keep the actor check before returning
     the recorded row.
2. **Phase 15 report year scoping.** `general_ledger(_exact)` and `trial_balance_exact` take a tax year. They
   should call `taxguard_ledger_year_guard(p_tenant, p_client, p_actor, r, p_tax_year)` immediately after
   `taxguard_ledger_actor`, as the Phase 14 `taxguard_ledger_read` and `taxguard_ledger_trial_balance` do.
   `ledgerYearScope.db` shows the expected refusal behaviour.
3. **Refund schema reconciliation.**
   - Phase 14 has `20261018010000` (refund records). Codex's `20261019020000` refunds fail after it (probe
     evidence in `phase14-phase15-billing-overlap.md`).
   - Required in the canonical migration: an owner-level immutability trigger, the reason in the audit, an
     explicit refusal of an incompatible existing schema, and the adapter contract in
     `src/tests-db/refundContract.ts`.
   - Phase 14 will switch `BillingStore.refund` to the seven-argument function once the canonical migration is
     published.
4. **Compatibility with the Phase 14 ledger triggers.**
   - The triggers read `creator_uid` (entries) and `prepared_by` (adjustments). Phase 15 inserts must keep
     writing those columns with the acting staff member's uid. A system or service uid that is not an active
     member of the tenant is refused with `LEDGER_ACCESS_DENIED`.
   - If Phase 15 redefines `taxguard_ledger_read`, `trial_balance`, `work_queue` or a book-to-tax function after
     070000, keep the one-line year check; `ledgerYearScope.db` fails if it is lost.
   - Monetary precision and idempotency are unaffected: the trigger reads only the tenant, client, author and tax
     year.
5. **Shared refund regression contract.** `src/tests-db/refundContract.ts` is implementation-neutral. Phase 14
   runs it through `phase14Adapter`. The canonical migration should add its own adapter so both implementations
   are measured against the same cases:
   - replay and key reuse;
   - concurrent submissions of one operation;
   - owner-level immutability;
   - the reason recorded in the audit;
   - unkeyed calls revoked;
   - over-refund;
   - tenant and client isolation.

   An adapter flag that is `false` documents a known gap and must not be read as a passing case.
6. **Financial reporting authorization.** Invoices carry an `engagement_id`, and every report takes a tax year,
   but `taxguard_bill_*` still authorizes per client.
   - Phase 15 billing and reporting should apply `taxguard_staff_record_scope` (proposal 20261018100000) to the
     invoice's engagement, and `taxguard_ledger_year_guard` to every report year.
   - Phase 14 does not change `taxguard_bill_*`, because Phase 15 redefines it.
7. **Safe case-team reassignment.** Proposal 20261018090000 makes the recorded preparer and reviewer count only
   while their live assignment exists, so a replacement assignee cannot act on the case. The reviewed operation
   should:
   - be manager-only, with a reason, audited, and with optimistic concurrency on the case version;
   - require the new person to hold the live assignment for that role and the case's engagement and year;
   - keep segregation of duties (preparer differs from reviewer, and the new reviewer did not prepare the
     current stage evidence or run a calculation awaiting their review);
   - never rewrite attestation history.

   This does not overlap Phase 15. Phase 14 can deliver it as the next package unless Codex claims it.
8. **Migration order and schema compatibility.**
   - Phase 14 proposals occupy execution positions 72–80 (`20261018020000` to `20261018100000`). Codex's Phase 15
     migrations are dated `20261019…` and must be ordered after them in `migration-execution-order.json`, with
     explicit `dependsOn` entries on any Phase 14 proposal whose functions or tables they touch:
     - 040000 (`taxguard_bill_transition`);
     - 070000 (ledger and book-to-tax functions, insert triggers);
     - 010000 (refund records).
   - A Phase 15 function that replaces a Phase 14 definition must be copied from the current (execution-order)
     definition, or it silently drops the Phase 14 checks. The DB suites `ledgerYearScope.db`,
     `billingTransitionAudit.db` and `billingRefunds.db` fail if that happens.
   - Both sides should run `npm run staging:migration:release-candidate` and `composition.db` (which re-applies
     every proposal and compares the schema, including function privileges) on the merged order before
     requesting owner approval.

## Integration readiness against Codex's Phase 15 branches (read-only, 2026-10-19)

The owner-approval plan for the version collision, refund withdrawal, merge steps and reproduction is
`phase14-phase15-migration-integration-plan.md`.

The ten `origin/codex/taxguard-phase15-*` branches were compared with `origin/main` (`6e31a40`). Nothing on those
branches was modified.

**Blocker: duplicate migration versions.** Both sides use the same version prefixes, and none of these is on `main`.

| Version | Phase 14 (PR #22) | Phase 15 (Codex) |
|---|---|---|
| `20261018000000` | `taxguard_case_validate_replacement_evidence` (`d24120f`, 2026-10-18) | `taxguard_financial_reporting` (`b1ce7d6`, 2026-10-18, on 10 branches) |
| `20261018010000` | `taxguard_billing_refund_records` (`8d76945`, 2026-10-18) | `taxguard_report_cent_transport` (on 9 branches) |

- `migration-execution-order.json` keys entries by full file name, so the review tooling tolerates the pair.
- Migration runners that key on the version prefix do not: the Supabase CLI records one row per version, so the
  second file of a pair would be treated as already applied or refused. One side must renumber before either
  merges. This is an owner and Codex decision.
- **Recommendation:** Codex moves its two reporting migrations to free slots after the Phase 14 proposals and
  before its own `20261019…` series, for example `20261018110000` and `20261018120000`. That keeps every Phase 15
  dependency order intact and leaves Phase 14's reviewed evidence, manifests and dossier unchanged.
- **The alternative,** renumbering Phase 14, touches 11 proposals, the manifests, the review bundle, traceability
  and this dossier, and invalidates their review evidence.

**Function overlap.**
- `20261019020000_taxguard_refund_idempotency` (5 branches) redefines `taxguard_bill_refund`, which Phase 14's
  `20261018010000` also defines. This is the documented refund reconciliation (item 3 above): wait for Codex's
  canonical migration.
- No other Phase 15 migration redefines a function changed by Phase 14 proposals `20261018000000` to `100000`.

**In-place edit of a shared proposal.** `codex/taxguard-phase15-financial-reporting-integrity` appends
`taxguard_ledger_general_ledger` to `20261012240000_taxguard_durable_ledger.sql`.
- The edit is additive: no existing definition changes, so the copies in `20261018070000` remain current.
- Editing an already-reviewed proposal in place weakens its review record. A new proposal is preferable, and the
  integrated branch already carries the function in `20261018000000_taxguard_financial_reporting`.
- The function authorizes with `taxguard_ledger_actor` only, so it needs the year guard (item 2 above).
