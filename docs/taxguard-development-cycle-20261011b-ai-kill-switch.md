## 3. Security notes

| Control | Evidence |
| --- | --- |
| Server-side enforcement | Test: A34 assessment succeeds, the stop is engaged, then the same assessment is refused with `AI_KILL_SWITCH_ACTIVE`. GLOBAL blocks all agents; a stop on another agent does not block A34. |
| Frontend cannot bypass | The UI only calls the API; enforcement reads `ai_kill_switches` on every assessment. |
| Tenant isolation | A tenant B stop does not affect tenant A. The HTTP test attaches a forged tenant B administrator `req.user` from the transport, and the stop is still written to the verified identity's tenant A. |
| Authority claims rejected | Bodies containing `tenant_id`, `activated_by`, `enabled` or unknown scopes return 400. |
| Audit immutability | The test harness confirmed that `ai_security_events` deletion is blocked (`AI_IMMUTABLE_HISTORY`); the tests were written to respect this rather than circumvent it. |
| Not in scope | Deactivation (H11); MODEL / TOOL / WORKFLOW scopes in the API. The schema supports them, but the target IDs need registry validation. The production path also requires `TAXGUARD_AI_GOVERNANCE_ENABLED=true` with durable infrastructure (E01). |

Behaviour change to note for operators: environments that relied on `SUPABASE_ANON_KEY` alone for the server will now report the database, authentication and storage providers as NOT_CONFIGURED. Production startup paths that call `getSupabaseAdmin()` will throw `SUPABASE_CONFIG_MISSING` until `SUPABASE_SERVICE_ROLE_KEY` is provided.
